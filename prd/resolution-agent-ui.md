# 代理界面与流程 PRD

| 项 | 内容 |
| --- | --- |
| 状态 | 已确认，按本文实现 |
| 分支 | `feature/resolution-agent-ui` |
| 范围 | 工作包全屏页右侧「代理」页签，以及管理里的代理设置页 |
| 基线 | 现有对话、结果按钮、内置状态、Gitea 规则都保留。这一支改的是呈现方式和哪些按钮在什么时候能按 |

## 1. 现在的问题

页签内容是 `panels/show.html.erb` 里的一段原始 HTML：标题、`<pre>` 白底正文、浏览器默认按钮。每一轮模型回复都把「当前结论 / 环境 / 问题 / 已做尝试 / 日志解读 / 代理给出的方向」整段摊开。Gitea 地址和分支一直露在输入框下面。七个结果按钮一次全摆出来。没有空状态、时间、滚动区域，错误也写进对话，看起来像代理自己说的。

流程上有四个洞：

1. 创建人可以在任何时候按「测试通过」。主管关闭只检查历史上有没有一次测试通过，所以可以跳过研发修复直接关闭。
2. 配置好的研发主管如果不是创建人或当前负责人，`Access#open?` 会拒绝打开页签，确认完成的按钮根本看不到。
3. 输入框里整段文字若正好是「已解决」「修复有效」「测试通过」等，会和按钮走同一条结果逻辑，状态会被改掉。
4. 下一次总结取的是最后一条代理消息的结构化内容。错误提示没有这份内容，于是环境、问题、日志会被写成「未提供」。

## 2. 目标

1. 页签看起来像 OpenProject 里的一块工作区：对话可读，结果动作和普通聊天分开，设置页用 Primer 表单。
2. 结果按钮只在当前阶段、当前角色下出现，并写明按下后状态会变成哪个内置状态。
3. 主管能打开待关闭的工作包并确认完成。
4. 只有结果按钮能改变状态和负责人。普通回复会追加到描述并新增活动评论，但不会改变状态或负责人。
5. 活动日志里的总结字段保持现在的七段，不改状态名。仍是 Tested、In progress、In testing、Closed。

## 3. 页签布局

页签名字已经是「代理」，内容区不再加同样的标题。

自上而下四块：

1. **阶段说明**，一行。写当前阶段，以及这个人现在能做的事。例如：「待现场结论。你可以描述现象，或记录已解决 / 未解决。」
2. **对话**。占满页签剩余高度，可滚动，新消息在底部。
3. **结果条**。只放当前允许的按钮。每个按钮旁有一句后果，例如：「状态将改为 In testing，并写一条总结评论。」
4. **输入区**固定在底部。多行输入框和发送按钮。生成过程中输入框和发送按钮禁用，对话末尾显示「正在生成回复。」

空对话时，中间用一句引导：创建人看到「写下现场现象」；其他人看到当前阶段允许自己做的那一件事。

### 3.1 消息怎么显示

| 种类 | 样子 |
| --- | --- |
| 用户 | 显示姓名和时间，正文换行，不再用 `<pre>` |
| 代理回复 | 像常见 AI 对话界面一样显示自然语言气泡。回答尽量是一段连贯文字，不使用固定字段填空 |
| 已记录的结果 | 单独一条卡片：结论、状态是否变化、负责人是否变化。和普通回复分开 |
| 错误、工作流拒绝、未配置 | Primer 提示条，不记成代理说的一句话 |

仓库、修复分支、Pull Request 在回复里显示为链接。令牌仍然不出现。

### 3.2 代码修复入口

Gitea 地址和分支默认不出现。只有当前负责人在「已交给研发」或「测试未通过」时，输入区里才有一项「尝试修复代码」。展开后才填写仓库地址和分支。两项都空着时，发送就是普通对话。创建人提交的这两项会被忽略。

### 3.3 多个负责人时

仍由创建人选择。列表显示姓名。按下某人后才继续刚才那个结果。未选择前，状态、描述、负责人都不变。

### 3.4 设置页

管理页改成 Primer 表单，分成四组：启用、服务账号与研发主管、模型、Gitea。字段含义、空密钥保留原值、地址和令牌的保存方式不变。

## 4. 阶段

阶段由结果记录决定，不由别人在工作包上手工改的状态决定。手工改状态不会让页签进入下一阶段。

| 阶段 | 进入条件 | 谁能操作 | 允许的结果 |
| --- | --- | --- | --- |
| 收集 | 还没有现场结论 | 创建人聊天 | 已解决、未解决 |
| 已交给研发 | 已记录已解决或未解决；或修复失败已交回 | 当前负责人聊天，并可展开代码修复 | 修复有效、修复失败 |
| 验收中 | 已记录修复有效 | 创建人写下测试情况 | 测试通过、测试未通过 |
| 测试未通过 | 最新测试记录是未通过 | 负责人可再做一次代码修复；创建人可再次记录测试 | 再次修复有效或修复失败；再次测试通过或未通过 |
| 待关闭 | 最新测试记录是通过 | 研发主管 | 确认完成 |
| 已关闭 | 已确认完成 | 能打开页签的人只读 | 无 |

补充规则：

- 「修复有效」要求这一阶段里已经有一次成功的修复记录，并且有 Pull Request 地址。
- 「修复失败」要求这一阶段里已经有过代码尝试。失败后状态不变，负责人回到这次尝试前记下的人。没有记下这个人时，负责人不变，对话里说明原因。
- 「确认完成」只看最新一条测试记录是通过。更早的一次通过不算。关闭前状态必须能写成 Closed。
- 现场结论只记录一次。已解决和未解决不能交替再按。
- 创建人同时是负责人时，收集阶段只显示现场结论；交给研发之后只显示研发动作。
- 主管能查看这条工作包时就可以打开页签。待关闭之前不显示确认按钮。管理员仍可打开自己能查看的工作包，用于排查；管理员不因此获得结果按钮。
- 已关闭后隐藏输入区和结果条。

按下结果按钮时，页面先写明将要发生的事，再提交。工作流拒绝、缺少服务账号、缺少内置状态时，描述、评论、负责人、状态保持按下之前的样子，并显示提示条。

## 5. 对话和活动日志

普通发送保存用户这句话和代理回复。每次成功回复后，把回答追加到 Overview 的 Description 末尾，并以服务账号在 Activity 新增同内容评论。普通回复不改变状态或负责人。Description 与 Activity 更新失败时保留对话回复，并显示提示条。

结果按钮成功后，活动日志仍写现在的总结：当前结论、环境、问题、已做尝试、日志解读、代理给出的方向。未解决时描述仍改成这份总结，并在末尾保留原始记录。其余结果只新增评论。

总结使用最近一条带结构化内容的代理回复。提示条和错误不参与这份内容。

关闭时的结论写成「已确认完成」。测试通过的结论仍是「测试通过」。

## 6. 不变的部分

- 一条工作包一条对话。
- 创建人、当前负责人、能查看该工作包的管理员可以打开。主管按第 4 节增加打开权限。
- 状态只使用内置名称 Tested、In progress、In testing、Closed。
- 第一次转交、关联工作包负责人、修复失败交回原负责人，规则不变。
- 只换负责人时不改状态。
- 外部文件只保留元数据。
- 修复分支仍是 `agent/<工作包编号>`，向原分支开 Pull Request，不向原分支推送。
- 模型或 Gitea 失败时不改工作包字段。

## 7. 验收

1. 打开工作包页签，能看到对话、阶段说明和输入区；没有七个按钮同时出现，也没有一直展开的 Gitea 输入框。
2. 新代理回复显示为一段自然语言，不显示环境、问题、尝试、日志等固定字段。
3. 发送「测试通过」这三个字只增加一条用户消息，状态不变。
4. 收集阶段只有创建人能记录已解决或未解决。记录一次后，这两个按钮消失。
5. 没有成功的 Pull Request 时，「修复有效」不出现。
6. 没有代码尝试时，「修复失败」不出现。
7. 创建人在修复有效之前看不到测试按钮；按过测试通过后，主管能打开页签并看到确认完成。
8. 主管不是创建人或负责人时，仍能打开待关闭的工作包并关闭它。最新记录是测试未通过时，不能关闭。
9. 一次错误提示之后再记录结果，活动日志里的环境、问题和日志仍来自上一份有效回复。
10. 设置页以分组表单保存，空着的密钥不会把已保存的值清掉。
11. 点击发送后，用户消息在一次短请求内出现；模型调用在后台进行，不占用页面请求。
12. 后台任务排队或执行时，每两秒更新一次状态，明确显示正在分析、读取代码、生成回复或创建修复。
13. 刷新、关闭页签或短暂断网不会取消后台任务；重新打开后仍能看到当前进度或最终结果。
14. 生成期间输入、发送和结果按钮都不可用。任务成功、失败或超时后停止轮询，并恢复当前阶段允许的操作。
15. 超时、连接、鉴权或配置、限流、模型格式和 Gitea 错误显示为提示条，不伪装成代理回复，也不修改工作包。
16. 同一段对话一次只能有一个生成任务。旧任务不能覆盖新任务的消息、状态或锁；已中断任务留下的锁可以安全恢复。
17. 完成轮询后，新回复以逐字动画显示；用户偏好减少动态效果时直接显示完整内容。
18. 每次成功回复都会追加到 Overview Description，并在 Activity 新增同内容评论，工作包 Status 保持不变。

## 8. 这一支不做什么

不改企业令牌，不新增状态，不改第一次交给谁，不合并 Pull Request，不在对话里读取其他工作包的描述、评论和附件。

## 9. 异步回复约定

发送普通消息时，Web 请求只校验权限和输入、保存用户消息并提交后台任务。页面立即重新显示页签，不等待模型或 Gitea。后台任务使用发起人的权限和语言环境，单次模型调用最多等待 180 秒，不自动重复同一次推理。

对话保存当前任务标识、后台任务编号、开始时间和阶段。开始新任务、更新阶段、写入最终结果和释放生成锁都必须核对任务标识。任务记录已经不在排队或执行、并且超过恢复时间后，才允许清理遗留的生成锁。

页面在任务运行期间每两秒读取一次只属于当前用户和当前工作包的状态，通过 Turbo Stream 更新对话与输入区。临时网络错误保留现有状态并继续轮询；页面离开或任务结束时停止。任务完成后滚动到最新消息。

状态顺序按实际执行步骤显示：

1. 排队中。
2. 正在分析工作包。
3. 代码请求正在读取仓库；普通对话跳过此项。
4. 正在生成回复。
5. 代码请求正在创建修复和 Pull Request；普通对话跳过此项。

页面断开不影响后台任务。后台异常必须把任务收尾为失败，并按错误类别显示可操作的提示；日志只记录工作包、任务、阶段和异常类别，不记录提示词、令牌或模型原始响应。
