# 工作包解决代理 PRD

| 项 | 内容 |
| --- | --- |
| 状态 | 第二稿。已并入 PE / R&D 流程审核意见。未开始实现 |
| 分支 | `feature/work-package-resolution-agent` |
| 读者 | 产品审核、后续实现 |
| 基线 | 当前 `dev`：工作包、关系、附件、评论日志、工作流、`modules/llm`。仓库里已有 GitHub / GitLab 集成，没有 Gitea 集成 |

## 1. 背景

两支团队共用一套 OpenProject。

**PE** 在现场遇到问题后，把问题记成 issue，打开这条 issue 上的代理对话框，按代理给出的方案在现场处理。

**R&D** 接收任务和 issue，负责修复。R&D 可以在对话里给出 Gitea 仓库地址和分支，让代理先尝试改代码。

管理员配置代理。任何人都可以使用。一次对话只针对用户当前打开的这一条 issue 或 task，不能在对话里读取或改写另一条。

## 2. 目标

1. PE 能在自己记下的 issue 上与代理对话，按方案现场处理。
2. 现场解决后，代理把问题、环境和方案写成总结，状态改为**验收**，并把负责人交给 R&D 侧。
3. 现场没有解决时，代理按 issue 格式把对话写进这条 issue，状态改为**进行中**，并把负责人交给 R&D 侧。
4. R&D 能在自己正在处理的 issue 或 task 上给出 Gitea 仓库和分支，由代理尝试修复。
5. 代码修复成功后，状态改为**验收中**。PE 现场测试并写下结果后，由 R&D 主管确认，状态改为**关闭**。
6. 代码没有修复成功时，把结果反馈给对应的 R&D 同事，这一步只换负责人，不改状态。
7. 发布到活动日志里的内容是一份总结：当前结论、环境、已做尝试、日志解读、代理给出的方向。

## 3. 角色

| 角色 | 使用方式 |
| --- | --- |
| PE | 创建现场 issue，与代理对话，按方案处理，事后填写现场测试结果 |
| R&D 同事 | 处理分配给自己的 issue / task，提供 Gitea 仓库和分支，让代理尝试修复 |
| R&D 主管 | 接收第一次转来的 issue 并分配给具体同事；PE 测试通过后确认完成，使状态变为关闭 |
| 管理员 | 配置模型、状态名称、两位主管、Gitea 连接、代理服务账号 |
| 代理服务账号 | OpenProject 中的一个真实用户。评论、负责人变更和状态变更记在这个账号下 |

「任何人都可以使用」指：凡是能打开某条工作包、并且是这条工作包的创建人或当前负责人的人，都可以在这条上打开对话。创建人覆盖 PE 所提的 issue。当前负责人覆盖主管分配之后的 R&D 同事。其他人不能对这条工作包打开对话。

一次对话绑定这一条工作包。代理不读取其他工作包的描述、评论和附件。为了决定负责人，允许只读取直接关联工作包的编号、类型和当前负责人。

## 4. PE 流程

PE 创建 issue 并打开对话。对话里 PE 补充现场现象。代理读取这条 issue 的描述、评论，以及 PE 上传的日志附件。

### 4.1 现场已经解决

PE 在对话里确认方案有效。代理随后做三件事：

1. 用第 7 节的总结格式写一条评论，内容是问题本身和已经生效的方案。
2. 把状态改为管理员配置的「验收」。
3. 按第 6 节指定负责人。

### 4.2 现场没有解决

PE 在对话里确认方案无效，或代理在一轮澄清后仍然无法给出可执行方案。代理随后做三件事：

1. 按第 7 节把对话整理进这条 issue 的描述，并写一条同样内容的评论。已有描述保留在文末的「原始记录」里。
2. 把状态改为管理员配置的「进行中」。
3. 按第 6 节指定负责人。

这两条是处理结果，会修改状态。它们和「只把负责人交给某人」不是同一种动作。

## 5. R&D 流程

### 5.1 尝试修复代码

R&D 同事打开分配给自己的 issue 或 task，在对话里给出：

- Gitea 仓库地址，必须属于管理员配置的 Gitea 站点
- 要基于的分支名

代理只在这次给出的仓库和分支上工作：

1. 读取该分支上与对话结论相关的代码。
2. 从该分支拉出修复分支，名称是 `agent/<工作包编号>`。
3. 把修改提交到修复分支，并在 Gitea 上打开一个指向原分支的 Pull Request。
4. 在对话里给出仓库、修复分支、Pull Request 地址，以及改了什么。

代理不向对方给出的那个分支直接推送，不处理这次未给出的仓库，不合并 Pull Request。

### 5.2 代码修复成功

R&D 同事在对话里确认修复有效。代理把状态改为管理员配置的「验收中」，并写一条总结评论，附上 Pull Request 地址。

然后由 PE 在现场测试。PE 在同一条工作包的对话里写下测试结果。测试通过后，R&D 主管在对话里确认完成，代理才把状态改为管理员配置的「关闭」。主管未确认时，代理不关闭。

测试未通过时，状态保持「验收中」，代理把 PE 的测试结果写成评论，负责人仍是当前 R&D 处理人。

### 5.3 代码没有修复成功

代理写明尝试过的修改和失败原因，把负责人改为这条 issue 对应的 R&D 同事。状态保持不变。

「对应的 R&D 同事」指确认开始修代码之前的当前负责人。开始时代理记下这个人，失败后交还给他。

## 6. 负责人怎么定

换人本身不修改状态。状态只在第 4 节和第 5.2 节的结果动作里改变。

| 情形 | 新负责人 |
| --- | --- |
| 这条 issue 第一次交给 R&D | 管理员配置的 R&D 主管。主管再分配给具体同事 |
| 这条 issue 有直接关联的工作包，且那个工作包已有负责人 | 那个负责人，不再经过主管 |
| R&D 代码修复失败 | 开始修复前的那位 R&D 同事 |
| 主管人工分配 | 主管在 OpenProject 里自行指定，代理不代替主管挑人 |

直接关联只包括父工作包、子工作包，以及类型为相关、阻塞、被阻塞、重复、包含、属于、依赖的一层关系。有多个关联且负责人不同时，代理在对话里列出这些人，由 PE 或当前用户选一个，不自动挑。

找不到主管账号，或关联工作包没有负责人时，不修改负责人，对话里说明原因。

## 7. 写入 issue 的格式

对话原文留在侧栏。进入描述和活动日志的是一份总结，字段固定为：

1. **当前结论**：已在现场解决、未解决并转交 R&D、代码已修复待验收、测试通过或测试未通过。
2. **环境**：设备、版本、现场配置、发生时间。对话里没有的项写「未提供」。
3. **问题**：现象、影响范围、是否可复现。
4. **已做尝试**：PE 或 R&D 已经做过的操作，以及结果。
5. **日志解读**：附件日志里的关键行和含义。没有日志则写「无日志附件」。
6. **代理给出的方向**：具体步骤；若是代码修复，附仓库、分支和 Pull Request 地址。
7. **原始记录**：仅在改写描述时保留改写前的原文。

评论和描述使用同一份正文。描述更新发生在 PE 未解决并转交时。其余结果只新增评论，不覆盖描述。

## 8. 对话产品

对话在工作包全屏视图的侧栏，标题为「解决代理」。一条工作包一条对话，刷新后恢复。同一条上同时只生成一轮回复。

能打开对话的人：这条工作包的创建人，以及当前负责人。管理员在配置页可以打开对话，以便排查，但不能借此查看自己无权查看的工作包。

代理回复包含第 7 节里已经能够确定的部分。材料里没有的事实写「未提供」，不补充未出现过的日志或代码。

PE 确认「已解决」或「未解决」之后，才执行第 4 节的写入和状态变更。R&D 确认「修复有效」之后，才改为验收中。主管确认「完成」之后，才关闭。

生成失败时保留用户刚才的话，负责人、状态、描述都不变。

## 9. 代理读取的材料

可见范围等于正在对话的这个用户。代理服务账号的权限不用于扩大可见范围。

当前工作包：

- 编号、标题、描述、状态、类型、优先级、负责人
- 最近 20 条评论
- 长文本自定义字段

附件：

- 全部附件的文件名、大小、类型、上传者、时间
- 文本、Markdown、CSV、JSON、日志文件的正文，用于第 7 节的日志解读
- PDF 只取文本层
- 图片仅在绑定模型具备视觉能力时送入模型
- 单个文本文件最多 100 KB，一次最多 10 个文件
- 压缩包、Office 二进制、音视频只列出文件名

外部存储上的文件链接只读取元数据：文件名、存储名称、路径。不下载文件正文。

其他工作包只读取直接关联项的编号、类型和当前负责人，供第 6 节使用。

## 10. 权限与配置

管理员在实例配置里完成全部配置，项目内不再单独开一套开关。

管理员配置：

- 启用或关闭代理
- 在现有 LLM 连接上绑定本功能。功能键名为 `work_package_resolution_agent`。模型需要工具调用和结构化输出
- 代理服务账号
- R&D 主管用户
- 四个状态分别对应 OpenProject 里的哪个状态：验收、进行中、验收中、关闭
- Gitea 站点地址和访问令牌。令牌只授予需要代理修改的仓库

使用对话不另设项目权限。门槛是第 8 节的创建人或当前负责人。

代理服务账号需要查看工作包、编辑工作包、添加评论。状态变更还要求它在工作流里拥有对应的跳转。工作流不允许时，这次结果动作整次取消：描述、评论、负责人、状态都保持动作前的样子，对话里写出工作流不允许的原因。

Gitea 令牌不出现在对话、评论和日志里。

## 11. 和现有系统的关系

- 模型连接使用 `modules/llm` 的 `Llm::Session` 和 `OpenProject::Llm::Features`
- 工作包的描述、评论、负责人、状态走现有更新服务和合约
- 附件使用工作包已有附件
- 外部文件链接只读 `Storages::FileLink` 的元数据
- Gitea 是新增连接，不复用 GitHub / GitLab 集成的账号模型
- `description_assistant` 仍只负责改写文字，本代理不调用它

## 12. 数据

| 记录 | 内容 |
| --- | --- |
| 对话 | 所属工作包、创建时间 |
| 消息 | 角色、正文、时间、是否已写成活动日志评论 |
| 一次运行 | 结论类型、读过的附件名、Gitea 仓库、源分支、修复分支、Pull Request 地址、开始修复前的负责人 |
| 实例配置 | 开关、模型绑定、服务账号、R&D 主管、四个状态的映射、Gitea 地址和令牌 |

## 13. 验收

1. PE 创建的 issue 上可以对话；另一名既不是创建人也不是负责人的用户打不开这条对话。
2. 在 issue A 的对话里不能读到 issue B 的描述、评论或附件。
3. PE 确认已解决后：活动日志出现第 7 节的总结，状态为验收，第一次转交时负责人为 R&D 主管。
4. PE 确认未解决后：描述变为第 7 节的格式且保留原始记录，状态为进行中，负责人规则与第 6 节一致。
5. 存在关联工作包且该包已有负责人时，新的结果动作把负责人设为那个人，不设为主管。
6. 只换负责人的失败反馈不改变状态。
7. 上传的日志附件会出现在「日志解读」里；外部存储文件只出现文件名和路径，正文不进入总结。
8. R&D 给出本站 Gitea 仓库和分支后，代理打开修复分支和 Pull Request，不推送到对方给出的原分支。
9. R&D 确认修复有效后状态为验收中。PE 写入测试结果且主管确认后状态为关闭。主管未确认时状态不是关闭。
10. 代码修复失败后，负责人回到开始修复前的 R&D 同事，状态不变。
11. 工作流不允许目标状态时，描述、评论、负责人、状态都不变。
12. 模型或 Gitea 请求失败时，工作包字段不变。

## 14. 交付顺序

| 阶段 | 交付 |
| --- | --- |
| 1 | 侧栏对话、读取当前工作包和日志附件、按第 7 节发布总结 |
| 2 | PE 的两种结果：验收并交给主管，或写成进行中并更新描述 |
| 3 | 关联工作包的负责人规则，以及修复失败时交还原负责人 |
| 4 | Gitea 修复分支与 Pull Request，验收中、现场测试结果、主管确认后关闭 |
